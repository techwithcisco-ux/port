# BranchPort

Multi-branch retail monitoring and audit platform for informal-market
retailers in Ghana. One Express API, one Postgres database, three
frontends (management dashboard, branch POS, market analytics).

## Architecture

```
                     ┌──────────────────────────┐
   browser ────────► │  branchport-api (Node)   │
                     │  Express + pg + JWT      │
                     └───────────┬──────────────┘
                                 │
                                 ▼
                     ┌──────────────────────────┐
                     │  branchport-db (Postgres)│
                     │  schema: apps/api/schema.sql
                     └──────────────────────────┘

   apps/dashboard  (:5173)  owner + manager web app
   apps/pos        (:5174)  staff till — offline-first (Dexie + sync queue)
   apps/market     (:5175)  cross-business analytics (platform admin)
```

All authentication and authorization lives in `apps/api`:

- Passwords are bcrypt-hashed by the API and never leave the server —
  clients only see the public user projection.
- Sessions are short-lived access JWTs (default 15 min) + rotating opaque
  refresh tokens (default 30 days, stored hashed, reuse-detected).
  Passwords require 8+ chars with a letter and a number; 5 bad attempts
  lock the account for 15 minutes.
- Roles (`owner`, `manager`, `staff`) are enforced by API middleware
  (`requireRole`), not by hiding buttons in the UI.
- POS staff authenticate by phone number after a one-time activation
  link (generated by the owner/manager from the dashboard).
- Market analytics uses a separate server-verified admin password
  (`MARKET_ADMIN_PASS`) that exchanges for a 12-hour `platform` JWT.

The trust model is unchanged from the original design:

- `sales`, `inventory_intake`, `inventory_allocations` are immutable —
  the API exposes INSERT but no UPDATE/DELETE for them.
- `audit_events` is append-only and written exclusively by `apps/api`
  on every mutation. No client can write to it directly.
- The owner role is the only role that can read `audit_events`. The
  manager and owner dashboards are the same app — what differs is
  which rows the API returns for the logged-in user's role.

## Repository layout

```
branchport/
  apps/api/              Express API: auth, REST data routes, platform
                         export. schema.sql is the single source of truth
                         for the database.
  apps/dashboard/        Management dashboard (manager + owner views).
  apps/pos/              Branch POS. React + Vite, offline-first via
                         Dexie (IndexedDB) + a sync queue.
  apps/market/           Market analytics: platform-wide stats, user
                         directory, item trends, usage graphs, reports.
  packages/shared/       Shared TypeScript types + the REST client
                         (createApiClient) used by dashboard and POS.
  backend/               Legacy Python/Django rebuild of the same app
                         (SQLite, server-rendered). Not part of the
                         Render deployment — kept for reference.
  scripts/vercel-build.mjs  Legacy single-domain Vercel build
                         (dashboard at /, POS at /pos/). Render is the
                         primary deployment path now.
  render.yaml            Render Blueprint: Postgres + API + 3 static
                         sites. This is the recommended deployment.
```

## Run it locally

You need Node 18+ and a local Postgres. Nothing else.

```bash
npm install

# 1. Create the database and apply the schema (once):
createdb branchport
psql postgresql://localhost/branchport -f apps/api/schema.sql

# 2. Start the API (reads DATABASE_URL):
DATABASE_URL=postgresql://localhost/branchport npm run dev:api   # :8080

# 3. Start any frontend (they default to http://localhost:8080):
npm run dev:dashboard   # http://localhost:5173
npm run dev:pos         # http://localhost:5174
npm run dev:market      # http://localhost:5175
```

Frontends read `VITE_API_URL` (see each app's `.env.example`). Set
`MARKET_ADMIN_PASS` on the API to enable market analytics login locally.

Then open the dashboard and sign up the owner account — the signup
screen creates the business and the owner user in one step, and every
user after that (manager, staff) is created from inside the dashboard.

## Deploy to Render (recommended)

`render.yaml` provisions the whole platform as one Blueprint:

1. Push this repo to GitHub.
2. On Render: **New → Blueprint**, select the repo. Render provisions:
   - `branchport-db` — Postgres 16
   - `branchport-api` — the Express API (generates `JWT_SECRET` and
     `MARKET_ADMIN_PASS`, health-checked on `/health`)
   - `branchport-dashboard`, `branchport-pos`, `branchport-market` —
     the three static frontends, each wired to the API's URL
     automatically.
3. Once the database is live, apply the schema once (from anywhere
   with `psql`, using the External Database URL from the Render
   dashboard):
   ```
   psql "$DATABASE_URL" -f apps/api/schema.sql
   ```
4. Open the dashboard URL and sign up the owner account. Fresh
   database, fresh signups — no legacy data.
5. Market analytics: read the generated `MARKET_ADMIN_PASS` from the
   Render dashboard (branchport-api → Environment) and sign in with it
   at the market URL.

See `DEPLOY.md` for details.

## Deploy to Vercel (frontends only)

The legacy single-project build still works: `vercel.json` + 
`scripts/vercel-build.mjs` compile dashboard and POS into one
deployment (dashboard at `/`, POS at `/pos/`). Point `VITE_API_URL`
at the Render API. Market analytics can be deployed as its own Vercel
project from `apps/market/`. You still need the Render (or any
Postgres-reachable) API — the frontends have no local backend.

## Environment variables

| Variable           | Where        | Purpose |
|--------------------|--------------|---------|
| `DATABASE_URL`     | apps/api     | Postgres connection string (required) |
| `JWT_SECRET`       | apps/api     | JWT signing secret (required in prod; API refuses to start without it) |
| `JWT_ACCESS_TTL`   | apps/api     | Access-token lifetime (default `15m`) |
| `JWT_REFRESH_DAYS` | apps/api     | Refresh-token lifetime in days (default `30`, rotating) |
| `MARKET_ADMIN_PASS`| apps/api     | Admin password for market analytics |
| `VITE_API_URL`     | all frontends| Base URL of the API (default `http://localhost:8080`) |
| `VITE_POS_URL`     | dashboard    | Deployed POS URL shown on the staff notice screen |
| `VITE_BASE`        | pos, market  | Vite base path for standalone deploys (`/` = site root) |

`.env` files are git-ignored — never commit real credentials.

## What's built

- Owner signup → manager/staff provisioning with phone-number POS
  activation links.
- Product setup, inventory intake, multi-branch stock allocation with
  retail-equivalent preview, supplier ledger with derive-not-store
  running balances.
- Owner audit log (entity/actor/date filters, before/after diffs) and
  owner flags panel (price anomalies, backdating, repeated
  overriders, frozen allocations).
- POS sell screen: offline-first Dexie queue + sync loop, true
  remaining stock (allocated − this branch's sold) computed fully
  offline, customer name/phone on the order, plus a staff inventory
  dashboard (revenue, top sellers, stock status, unsold items).
- Market analytics: platform stats, user directory, items tracker,
  live market ticker, usage analytics, CSV reports — all fed by
  `GET /platform/export` with a platform JWT.
- Responsive UI throughout; the POS is a phone-screen PWA.
